# Forecast review (0.9.70)

Overview links to `/projects/{project}/forecasts`. This page generates server-side review predictions for Google site clicks, the five highest-impression observed queries and five pages in the last 28 days, plus GA4 Organic Search sessions and key events. These review predictions have their own method labels; the Overview's existing browser prognosis retains its separately labelled models. All reads use persisted scoped repositories. No provider request or import is triggered.

## History and models

Training reads up to 486 stored dates independently of the Overview display range. Missing query/page dates remain unknown, including a key absent from a completed import. GA4 successful empty import dates are genuine zero observations; limited/thresholded history is withheld. GA4 property, currency and timezone are bound to predictions. Google property/domain and link timestamp are bound as well; changing the binding prevents unrelated actuals from scoring old predictions.

Each metric needs 56 observed dates, a latest observation within seven days and at least 90% coverage in its fit window. Candidates are 28-day mean/trend, 56-day weekday average, previous-year calendar values and explicitly recorded event dates. Calendar patterns need 366 observed dates, a full-year span and every previous-year target; unmatched leap days are not invented. Named event predictions require two earlier observed occurrences for every matching target event, a weekday baseline excluding known event days, and at least four shared disjoint event-containing test windows. A date first entered after a test origin cannot appear in that origin's model.

At most eight disjoint test windows compete at 7/14/28-day horizons; targets need at least 90% observed dates. Model comparisons use the identical intersecting origins and target dates. Four shared windows are required; otherwise the recent-average fallback is explicitly unvalidated. Annual/event assistance must lower MAE by at least 5% against the best simple candidate. Predicting an event's date never assumes a beneficial traffic uplift.

## Forward records and calibration

Project editors explicitly save eligible review forecasts and enable weekly tracking through a CSRF-protected POST. Tracking can be paused. Opening a page never writes. Predictions are generated on the server; the client cannot submit fabricated points or outcomes. Issuance uses Clock's UTC date, and every target is strictly after it even when imported history lags. The snapshot includes daily predicted points, endpoint, selected method, dates, sample, backtest error, source digest and model version. A scoped unique key preserves the first prediction for the same issue date, horizon, source/binding and version. Existing predictions are never retrained or overwritten by scoring.

Later GETs score only past endpoints that have actual observations under the unchanged binding, or previously accepted saved actuals. Current provider corrections may change the actual and measured error; they never replace the issued prediction. Historical series can be read directly by saved key even after dropping out of the current top-five sample. Daily tracking saves accepted actuals so scoring survives the review's 486-day source-read window or later source-history removal. Historical accepted outcomes remain evidence for their original binding; new bindings cannot use them for calibration. Saved ranges receive within/outside results only when an actual exists. Missing or restricted outcomes without accepted saved evidence remain unknown.

Calibration groups by source, binding, method, model version and horizon. Select completed forward forecasts chronologically, excluding overlapping issue-to-target windows. MAE is unavailable with no outcomes. The 80% finite-sample conformal absolute-residual rank is `ceil((n + 1) * .8)`, requiring 20 disjoint observations; lower count means no range. Counts are bounded below by zero. This empirical target is not a coverage guarantee under time dependence or distribution changes. Backtest errors never enter forward calibration. At most 5,000 latest snapshots are read and 50 shown; actual reads are capped at 50 source bindings per pass. Full point arrays stay in the database and are omitted from history/calibration reads to bound memory. No historical success is manufactured before deployment.

Hourly dispatch queues up to 50 enabled, unchecked active projects with project/workspace identifiers only and a daily idempotency key. Each queue job resolves the current active project in its workspace, records matured outcomes and attempts all three horizons every seven days. Paused/deleted projects do not issue forecasts. Deadline/lease checks stop partial work safely; persisted predictions remain idempotent. No job calls a provider. This cadence lets a stable 28-day model eventually collect twenty non-overlapping outcomes; collecting that history takes at least 560 days rather than fabricating it from old backtests.

Changes to prediction or scoring semantics must increment `ForecastEngine::VERSION`; calibration must not merge errors from different algorithms under an unchanged version. Previously issued payloads remain immutable across upgrades.

## Event dates and storage

Project editors can record up to 200 named calendar occurrences within the stored-history window or next two years. Dates and names are validated, escaped and audited. Repeat insertion preserves when SCC first knew an occurrence. An incorrect occurrence can be excluded; its exclusion date preserves what was known at earlier origins. Conflicting names on one date or unknown held-out event outcomes block event assistance. Public holiday dates are not guessed from a domain, timezone or locale; the project's explicit calendar supplies dates. Freshly populated calendars remain gated until sufficient historical windows exist.

Additive migration `000062` creates `forecast_snapshots`, `forecast_calendar` and `forecast_tracking`; prior tables, credentials and signed 0.9.69 packages remain unchanged. Signed 0.9.70 installer/updater include this feature and migration; live installation is not performed by package preparation. Existing ProjectsEdit authorizes writes; existing project authorization protects reads. Repositories also enforce active workspace/project context and scope every snapshot/calendar read and write. No new runtime dependency, SQL in a controller/view, browser storage, provider credential access or paid job.
